# 한국어 기술 문서 작성 스킬

요청의 주 결과물이 동료 엔지니어가 읽을 한국어 기술 문서 본문일 때 적용한다.

**원본 가이드는 위키에 있다**: `LLM-WIKI/guides/korean-tech-writing/` (규칙 전체, 반려 사례, grep 검수 체크리스트). 이 스킬은 압축본이다. 공유되는 문서(제안서, 조사, 연구 방향)를 쓸 때는 원본 가이드, 특히 `reader-context-order.md`와 `empty-declarations.md`를 읽고 쓴다.

## 적용 범위 확인

작업을 시작하기 전에 아래 조건을 모두 확인한다.

- 사용자가 한국어 산문 형태의 결과물을 요청했다.
- 결과물이 이슈, 운영 기록, 연구 노트, 기술 가이드, 기술 코멘트 등으로 남는다.
- 코드나 파일 변경을 수행하는 과정이 아니라, 문서 본문 작성 자체가 요청의 중심이다.

조건을 충족하지 않으면 이 스킬의 어체를 작업 응답이나 진행 상황 보고에 적용하지 않는다. 사용자가 스킬을 명시적으로 지목한 경우에는 적용한다.

## 독자와 서술 대상 (문장 규칙보다 먼저 적용)

쓰기 전에 독자를 한 문장으로 정한다: "이 문서를 읽는 사람은 X를 알고 Y를 모른다". 공유되는 문서(조사, 연구 방향, 제안서, 가이드)의 독자는 이 작업을 지켜보지 않은 사람이다. 대화 내용, 폴더 구조, 프로젝트 진행 이력, 사용한 도구를 모른다.

가치는 대상에 대한 콘텐츠에서 나온다. 작업 과정에 대한 서술은 그 과정을 지켜본 사람에게만 읽히므로, 과정이 알아낸 것을 대상에 대한 사실로 바꿔 쓴다.

| 금지 패턴 | 예시 | 대체 |
|---|---|---|
| 조사 이력 서술 | "1차 조사에서 놓쳤던", "검색 축을 바꿔 다시 조사했더니" | 찾은 내용 자체를 서술 |
| 도구·주체를 근거로 | "Codex도 같은 결론에 도달했다", "에이전트 105개로 검증했다" | 근거를 대상에 두기: 논문, 데이터, 측정값 |
| 내부 진행 어휘 | "판정 갱신", "닫힘/생존", "채택할 것", "N차" | 독자 기준으로: "직접 선행연구가 있다", "아직 연구가 없다" |
| 내부 참조 축약 | 파일명, 문서 별칭, 사람 이름+산출물 약칭 | 내용으로 풀거나 첫 등장에서 정의 |
| 과정 회고를 성찰로 | "이번 조사에서 배운 것: 검색은 두 축으로" | 대상에 대한 이해를 쓰기: 문제의 구조, 왜 그런가 |

예외: 운영 기록과 이슈 코멘트는 독자가 작업 맥락을 공유하므로 과정 서술("확인해보니", "로그를 보니")이 곧 내용이다. 구분 기준은 독자가 그 맥락을 아는가이다.

## 톤

엔지니어가 동료에게 "이런 일이 있었고, 이렇게 했고, 이렇게 판단했다"를 설명하는 톤으로 쓴다.

- 1인칭 서술체: "확인했습니다", "바꿨습니다", "~로 판단했습니다"
- 발견 과정을 이야기하듯: "확인해보니", "로그를 보니"
- 판단을 직접 밝힘: "~로 보입니다", "~해서 계속 진행하겠습니다"
- 괄호 안에 부연 캐주얼하게: "(디버깅 코드를 추가하고 test collector 배포하여 정보 수집중)"

## 쓰지 않는 문장 구조

LLM이 습관적으로 쓰는 구조들이다. 판단한 내용을 바로 서술하는 문장으로 대체한다.

| 금지 패턴 | 예시 | 대체 |
|---|---|---|
| 부정-대비 | "A가 아니라 B입니다", "~라고 볼 수는 없습니다", "A는 아니고 B에 가깝습니다" | B를 바로 서술 |
| 분석 보고서 어투 | "핵심 증거입니다", "같은 결론을 지지합니다", "가장 자연스러운 해석은" | 관찰한 것을 직접 서술 |
| 과장/추상 비유 | "최종 승자", "붕괴", "수축", "surviving", "닫는다(close 번역)", "연구가 붐빈다/얇다", "조용히 손상", "무인 운전" | 실제 현상을 직접 서술: "논문이 빠르게 나온다", "심사 통과 결과가 적다", "손상이 검사 없이는 드러나지 않는다" |
| 메타 프레이밍 | "이 문서는 ~를 설명하기 위한 기록이다", "이번 사건의 교훈은", "중요한 점은 ~이라는 것입니다" | 삭제. 내용 자체가 그 역할을 함 |
| 방어적 부정 | "~를 만들기 위한 게 아니고", "단순히 ~만 보는 게 아니고" | 삭제하고 긍정문만 남기기 |

## 언어 선택

- 한국어로 충분히 표현되는 영어는 한국어로: "lineage" → "경로/데이터", "canonical" → "원본", "corpus" → "데이터셋", "fallback" → 구체적으로 뭘 했는지 풀어쓰기
- 해당 분야에서 정착된 기술 용어(carry-in, change point, compaction, partitioned merge 등)는 영어 그대로 유지
- 학술 용어는 뜻을 풀어서: "환원되지 않는다" → "하나를 해결해도 나머지가 따라 해결되지 않는다"
- 영어 직역투 피하기: "동결" → "확정", "닫힌" → "통과한/확인한", "의미론" → "동작"

## 표기

- em-dash (—)와 en-dash (–)는 쓰지 않는다. 마침표, 쉼표, 콜론, 괄호로 문장을 재구성한다. 숫자 범위는 물결: 2~3주, 53~60%.
- 한글 뒤 여는 괄호 앞에 띄어쓰기 하나: "괄호 ()". 닫는 괄호 뒤 조사는 붙인다: "성능 (public score)을".
- 나머지 표기·검수 규칙 (grep 체크리스트 포함)은 원본 가이드의 formatting-and-report-style.md.

## 분량

- 같은 말을 다른 표현으로 반복하지 않는다
- 로그나 코드 블록 앞뒤로 같은 내용을 산문으로 반복하지 않는다. 블록 자체가 설명이면 추가 해석 불필요

## 지키는 것

- 기술적 사실(수치, 로그, 코드, 경로, 날짜)은 바꾸지 않는다
- 정착된 기술 용어를 억지로 한국어로 바꾸지 않는다
